# Problem Context: Search Not Returning Recent Documents

## Problem Statement

Users report that search queries for recent content (Nov 2025 - Jan 2026) are not returning expected results. Specifically, when searching for "Marmic calls from Nov 1, 2025 to Jan 13, 2026", only one old result from Nov 13, 2025 is returned, despite 37 Marmic Gong call chunks from Jan 2026 existing in Vespa.

## Symptoms

1. Search for "Marmic calls from Nov 1, 2025 to Jan 13, 2026" returns only 1 call from Nov 13, 2025
2. Even explicit "Marmic GONG calls" query returns wrong results (old Zendesk tickets)
3. Users (Sharon) report this used to work recently - this is a regression
4. No code was deployed recently

## Verified Facts

### Documents ARE in Vespa
- Direct Vespa query for GONG + Marmic + Jan 2026 returns 37 chunks
- "Marmic Weekly Sync" (Jan 5, 2026) and "Marmic/ST Weekly Sync" (Jan 12, 2026) confirmed present
- doc_updated_at timestamps are correct (1768233553 = Jan 12, 2026)

### Documents ARE in PostgreSQL
- 18,306 documents synced since Nov 1, 2025
- Most recent sync: Jan 13, 2026 16:40:31
- Gong connector is ACTIVE and running

### What's NOT Working
- Application search returns old Zendesk tickets instead of recent Gong calls
- Generic "Marmic calls" search (without source filter) returns Zendesk tickets from 2021
- Date-specific queries don't apply time filters

## Investigation Findings

### Bug Found: enable_auto_detect_filters defaults to None
- In `RetrievalDetails` class: `enable_auto_detect_filters: bool | None = None`
- In `preprocessing.py:82`: `if not search_request.enable_auto_detect_filters:`
- Since `None` is falsy, `if not None` evaluates to True
- This DISABLES LLM filter extraction for source_type and time_cutoff
- Result: Source filters (GONG) and time filters never get extracted from queries

### Preprocessing Time Confirms Bug
- `retrieval_preprocessing took 0.024 seconds` (from logs)
- Too fast for LLM filter extraction (which takes 1-2 seconds)
- Confirms filter extraction is being skipped

### Recency Bias Settings
- Default persona (id=11) now set to `FAVOR_RECENT` (we changed it)
- Was previously `BASE_DECAY`
- Recency bias formula: `max(1 / (1 + decay_factor * age_years), 0.75)`
- Only provides 25% reduction for old docs - may not be enough to overcome score differences

### LLM Filter Extraction Settings
- Default persona (id=11): `llm_filter_extraction = true` (we changed it)
- But this setting is never reached due to the None bug above

### Embedding Model History
- Current: `nomic-ai/nomic-embed-text-v1` (768 dim) - PRESENT
- Previous: `intfloat/e5-base-v2` (768 dim) - PAST
- Oldest: `thenlper/gte-small` (384 dim) - PAST

## Key Finding: Test Server Works, Production Doesn't

**Critical Discovery (Jan 13, 2026)**:
- Test server's Default agent successfully finds Gong calls for same query
- Test server's Sales Assistant also works
- Production's Default agent returns old Zendesk tickets instead
- Both servers running same codebase

This proves the bug in `enable_auto_detect_filters` is NOT the sole cause, since both servers have the same bug but test server works.

## Possible Explanations for Test vs Production Difference

1. **Persona settings differ** - Test server may have different recency_bias or llm_filter_extraction settings
2. **Container restart needed** - Production persona changes via SQL may not have taken effect (memory cache)
3. **Document volume** - Production may have more old documents drowning out recent ones
4. **Vespa index state** - Different embedding quality or indexing completeness
5. **Server restore impact** - Production was restored from backup Jan 8, 2026 - could have affected Vespa state

## Key Question

Why did this regress without code changes? Options:
1. Database/persona settings changed
2. Document volume reached a threshold where old docs dominate
3. Embedding model change affected ranking
4. Some other configuration change
5. **NEW**: Server restore from backup may have affected Vespa data or settings
