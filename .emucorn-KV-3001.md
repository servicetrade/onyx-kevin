## Bugs (Must Fix - Executable Problems)

### 1. SlackChannelConfig.from_model passes raw SQLAlchemy ORM objects instead of Pydantic models

- **File**: `/Users/ericburns/src/onyx-kevin/backend/onyx/server/manage/models.py:296-298`
- **Failure Path**: When any Slack bot admin API endpoint (e.g., `GET /admin/slack-bot/config`, `POST /admin/slack-bot/channel`) calls `SlackChannelConfig.from_model()`, the `standard_answer_categories` field receives a list of SQLAlchemy `StandardAnswerCategory` ORM objects (from `onyx.db.models`), but the Pydantic field at line 274 expects `list[StandardAnswerCategory]` (the Pydantic BaseModel at line 29). The `ConfigDict(arbitrary_types_allowed=True)` suppresses the Pydantic validation error at construction, but when FastAPI serializes the response to JSON, the ORM objects lack proper Pydantic serialization and will either fail or produce unexpected output (including `_sa_instance_state` internals).
- **Evidence**: Line 296-298 shows `standard_answer_categories=list(slack_channel_config_model.standard_answer_categories)` which passes raw ORM objects. The original upstream code (commit `913f7cc7d`) properly converts via `[StandardAnswerCategory.from_model(m) for m in ...]`. This bug was introduced in the `servicetrade` branch commit chain (`bb6520e09` added `arbitrary_types_allowed` as a workaround, then `b27a70b28`/`bc06bb0c3` added the Pydantic class but never updated `from_model` to use it).
- **Fix**: Change line 296-298 from:
  ```python
  standard_answer_categories=list(
      slack_channel_config_model.standard_answer_categories
  ),
  ```
  to:
  ```python
  standard_answer_categories=[
      StandardAnswerCategory.from_model(sac)
      for sac in slack_channel_config_model.standard_answer_categories
  ],
  ```
  And remove `model_config = ConfigDict(arbitrary_types_allowed=True)` at line 278 since it was only needed for this workaround.
- **Regression Test**: Yes - test that `SlackChannelConfig.from_model()` produces valid JSON-serializable output
- **Confidence**: High
- **Note**: The comment `# XXX this is going away soon` suggests this feature is being deprecated, but until it is, this is a real serialization bug affecting all Slack bot config API endpoints (4 call sites in `slack_bot.py`).

### 2. DEFAULT_PERSONA_ID hardcoded to deployment-specific ID 11

- **File**: `/Users/ericburns/src/onyx-kevin/backend/onyx/configs/constants.py:48`
- **Failure Path**: If this code is deployed in ANY environment other than the specific staging instance where persona ID 11 exists (the custom "Default" persona), the following code paths will fail:
  - `chat_utils.py:60` - `persona_id=persona_id or DEFAULT_PERSONA_ID` will try to create chat sessions with non-existent persona 11
  - `handle_regular_answer.py:123` - `get_persona_by_id(DEFAULT_PERSONA_ID, user, db_session)` will raise an error when Slack bot tries to answer questions
  - `shared_graph_utils/utils.py:162` - `get_persona_by_id(DEFAULT_PERSONA_ID, None, db_session)` will fail during agent search
- **Evidence**: `DEFAULT_PERSONA_ID = 11` at line 48. The original value was `0` (the built-in "Search" persona which exists in all deployments). ID 11 is a custom persona that only exists in this specific staging deployment.
- **Fix**: Revert to `DEFAULT_PERSONA_ID = 0` or make this configurable via environment variable. If the intent is to use a custom persona for Slack bot flows, that should be configured per-deployment, not hardcoded in source.
- **Regression Test**: Yes - test that DEFAULT_PERSONA_ID references a universally-available persona
- **Confidence**: High

## Critical Issues (Must Fix Before Complete)

### 3. SQLAlchemy error details leaked in API response

- **File**: `/Users/ericburns/src/onyx-kevin/backend/onyx/server/manage/reports.py:62`
- **Problem**: `detail=f"Database error when fetching chat session data: {str(e)}"` exposes internal database error details (table names, column names, query fragments, connection strings) to API consumers.
- **Impact**: Information disclosure. While this is an admin-only endpoint (`current_admin_user` dependency), it still violates defense-in-depth principles. SQLAlchemy errors can contain connection strings, table structures, and query details that shouldn't be in API responses.
- **Solution**: Replace with a generic error message and log the actual error server-side:
  ```python
  import logging
  logger = logging.getLogger(__name__)
  # ...
  except SQLAlchemyError as e:
      logger.error(f"Database error in chat-session-groups: {e}")
      raise HTTPException(
          status_code=500,
          detail="An internal error occurred while fetching chat session data.",
      )
  ```
- **Confidence**: Medium (admin-only reduces severity, but still a security anti-pattern)
